# N.O.V.A. 2026 대회 규칙·환자 상호작용·SOAP 작성 가이드

> 이 문서는 2026-10-13 기준 NOVA 공식 공개 문서와 공개 샘플을 바탕으로 한 **내부 개발·복기용 문서**다. 비공개 증례, 내부 프롬프트, 증례별 비공개 채점 기준은 포함하지 않는다. 공식 규칙이 변경되면 공식 사이트를 우선한다.

## 0. 먼저 구분하기

NOVA 실행에는 서로 다른 세 가지 역할이 있다.

| 역할 | 하는 일 | 공개 샘플 검증 | 공식 평가 |
|---|---|---|---|
| Doctor Agent | 질문, 공감·설명, 신체진찰 요청, 최종 진단·SOAP 제출 | `gpt-oss-20b` 세션 모델 | 지정 Doctor API 또는 본선 등록 모델 |
| 가상 환자·진찰 판정 | SAY에 환자 답변, EXAM에 진찰 결과 반환 | 서버의 샘플용 모델(공식 가이드상 `gpt-6-luna`) | 공식 서버의 평가용 모델(공식 가이드상 `gpt-6.1-sol`) |
| 평가 모델 | 대화·진찰·검사 로그와 SOAP·주진단을 평가 | 공개 샘플 참고 점수 | 공식 평가 점수 |

핵심은 다음과 같다.

1. **환자 모델과 평가 모델은 다르다.** 환자 모델은 진료 중 답하고, 평가 모델은 진료가 끝난 뒤 점수를 계산한다.
2. **Doctor Agent의 20B가 환자 답변을 만드는 것이 아니다.** Doctor가 서버 API에 행동을 보내면 서버 측 가상 환자가 답한다.
3. **공개 샘플과 공식 평가는 같은 모델이 아니다.** 공개 샘플은 공식 동작 계약을 연습하는 참고 환경이고, 공식 평가는 비공개 증례와 공식 평가 모델을 사용한다.
4. 공개 샘플 ZIP의 `patient_script`, `exam_results`, `model_record`는 개발자 복기용 자료다. 실제 Doctor Agent에게 실행 시작부터 전체 대본을 넣으면 안 된다.
5. 이 저장소의 CPX 채점기 결과는 **우리 팀의 로컬 참고 점수**다. NOVA 공식 점수와 같은 이름으로 표시하거나 대체하지 않는다.

## 2. 실행 모드

### 2.1 로컬 개발 키트

`develop.py`를 사용하는 모드다.

- 서버 없이 내 컴퓨터에서 실행한다.
- 가상 환자·진찰 판정·Doctor 모델을 OpenAI 호환 로컬 모델 등으로 지정할 수 있다.
- 서버와 같은 행동 규칙을 연습한다.
- 크레딧을 사용하지 않는다.
- NOVA 공식 점수를 반환하지 않는다.
- 결과는 보통 `transcript.json`, `record.json`으로 복기한다.

따라서 로컬 개발 키트에서 나온 환자 답변은 **공개 NOVA 서버의 환자 답변과 동일하다고 가정하면 안 된다.**

### 2.2 공개 샘플 서버

시작 패키지의 `sample.py` 또는 이 저장소의 원격 샘플 실행 경로를 사용하는 모드다.

- 개발 키로 NOVA 공개 샘플 세션을 시작한다.
- Doctor Agent는 서버가 제공하는 세션 API를 호출한다.
- 시작 정보 외의 환자 대본 전체는 Doctor Agent에 전달하지 않는다.
- `SAY`를 보내면 서버의 가상 환자가 답하고, `EXAM`을 보내면 서버의 진찰 판정 모델이 결과를 반환한다.
- 샘플 검증의 참고 점수는 공식 대회 점수와 다를 수 있다.

공개 샘플 서버에서 실제로 오가는 정보는 다음처럼 생각한다.

```text
Doctor Agent
    │  SAY / EXAM / DIAGNOSE
    ▼
NOVA 공개 샘플 서버
    ├─ 가상 환자 모델: 환자 답변
    ├─ 진찰 판정 모델: EXAM 결과
    └─ 샘플 평가 모델: 참고 점수
```

### 2.3 공식 평가

공식 평가는 공개 샘플과 계약은 유사하지만 다음이 다르다.

- 증례가 비공개다.
- 실행 토큰과 공식 실행 환경이 사용된다.
- 환자·진찰 판정·공식 평가 모델이 공개 샘플과 다를 수 있다.
- 공식 점수의 세부 프롬프트와 증례별 정답 기준은 공개되지 않는다.
- 예선·본선의 모델 사용 방식과 제출 조건은 해당 공지와 규칙을 우선한다.

## 3. Doctor가 처음 받는 정보와 환자 답변

### 3.1 처음 받는 정보

실제 세션에서 Doctor Agent가 처음 받는 것은 증례의 **시작 정보**다. 일반적으로 이름·나이·성별·주호소·시작 발화·제공된 활력징후 등 공개된 시작 정보가 여기에 해당한다.

공개 샘플의 `patient_script` 전체, `exam_results` 전체, `model_record` 전체는 시작 입력에 포함시키지 않는다. 이것들은 개발자가 공개 샘플을 이해하고 결과를 복기하기 위한 자료다.

### 3.2 환자 답변의 원칙

- 환자는 Doctor가 보낸 `SAY`에 반응한다.
- 묻지 않은 세부 병력·증상은 먼저 전부 말한다고 가정하지 않는다.
- 환자의 짧은 답변에는 다음 질문으로 확인해야 할 정보가 남을 수 있다.
- 환자가 말한 과거 진단이나 자기 추측은 사실 확정이 아니라 환자 진술이다.
- 위험 신호는 주호소에 맞춰 직접 확인해야 한다.
- `EXAM`은 요청한 특정 진찰 하나의 결과를 받는 행동이다.

### 3.3 시작 발화의 해석

공개 샘플에 긴 시작 발화가 정의되어 있으면, 그 발화가 처음 제공되는 것은 정상이다. 반대로 시작 정보에 없는 숨은 대본 전체를 처음부터 화면이나 Doctor 프롬프트에 노출하면 대회 조건과 달라진다.

즉, 공개 샘플의 시작 발화가 자연스러운지 여부와 별개로, 샘플 원문에 정의된 시작 정보를 임의로 축약하거나 추가하지 않는다. 비공개 대회 증례에 대해서는 시작 정보만 전달되는 실행 계약을 유지한다.

## 4. 행동 API와 턴 규칙

| 행동 | 의미 | 공식 규칙 |
|---|---|---|
| `SAY` | 질문·설명·공감 | 한 턴, NFC 정규화 후 30 코드 포인트 이하 |
| `EXAM` | 신체진찰 요청 | 구체적인 진찰 동작 하나, 30 코드 포인트 이하 |
| `TEST` | 혈액·영상 등 검사 요청 | 본선만 사용. 한 번에 검사 하나 |
| `DIAGNOSE` | S/O/A/P 기록과 주진단 제출 | 0턴. 제출하면 진료 종료 |

공통 규칙:

- 증례당 최대 50턴이다.
- `SAY`, `EXAM`, `TEST`의 입력 글자 수는 공백·문장부호를 포함해 NFC 정규화 후 계산한다.
- `SAY`는 환자에게 질문·설명·공감을 보내는 행동이다.
- 한 번의 `SAY`에 질문을 여러 개 묶으면 환자 답변과 정보수집이 불안정해질 수 있다. 한 턴에는 하나의 임상 목적을 둔다.
- 한 번의 `EXAM`에 여러 진찰을 묶지 않는다.
- 진료 종료 때 `DIAGNOSE`를 보내며 대화 턴을 추가로 사용하지 않는다.
- SOAP 기록은 `SAY`·`EXAM`의 30자 제한 대상이 아니다. 단, 전체 기록·주진단의 바이트 제한은 지킨다.
- 마지막 교육·설명은 기록의 `education`만 채우는 것으로 끝내지 말고 실제 `SAY`로 환자에게 설명한다.

### 4.1 턴을 쓰는 입력 오류

공식 규칙에 따라 다음 오류는 턴을 소모할 수 있다.

- 빈 내용
- 30 코드 포인트 초과
- 인식할 수 없는 EXAM
- 한 번에 여러 행동을 요청한 EXAM
- 실제 진찰이 아닌 내용을 EXAM으로 보낸 경우

예선에서 사용할 수 없는 `TEST`나 제공되지 않는 검사는 별도 오류로 거절될 수 있으며, 정확한 턴 처리와 오류 코드는 실행 환경의 SDK 응답을 따른다. 우리 로컬 CPX 서버는 공식 공개 규칙을 기준으로 이 동작을 재현한다.

### 4.2 구체적인 EXAM 작성

좋은 예:

```text
복부를 촉진하겠습니다
머피 징후를 확인하겠습니다
양측 하지 부종을 확인하겠습니다
```

피해야 할 예:

```text
전신 진찰을 해 주세요
이상 소견을 모두 알려 주세요
복부와 흉부와 신경학적 진찰을 한꺼번에 해 주세요
```

진찰 결과는 실제로 받은 뒤 O의 `exam`에 기록한다. 하지 않은 진찰을 정상이라고 채우지 않는다.

## 5. 공식 점수 구조

공식 공개 안내의 총점은 100점이다.

| 영역 | 배점 | 평가 초점 |
|---|---:|---|
| 정보수집 | 25 | 주호소에 필요한 문진·위험 신호·관련 계통 문진·진찰을 실제로 수행했는가 |
| 진단추론 | 15 | 주진단, 근거, 감별진단이 수집된 사실과 일치하는가 |
| 검사·추적 | 10 | 필요한 검사 계획과 재평가·추적 계획이 있는가 |
| 안전 | 15 | 응급 위험, 금기, 악화 시 대응, 안전망을 고려했는가 |
| 의사소통 | 15 | 환자에게 이해하기 쉽게 설명하고 걱정·이해도를 확인했는가 |
| 효율 | 20 | 불필요한 질문·중복·무관 행동과 모델 사용 비용을 줄였는가 |

### 5.1 무엇을 평가하는가

평가 대상은 다음의 조합이다.

1. Doctor Agent가 실제로 보낸 대화
2. 실제로 수행한 EXAM과 받은 결과
3. 본선에서 실제로 요청·수령한 TEST 결과
4. `DIAGNOSE`로 제출한 구조화된 SOAP
5. 별도로 제출한 주진단
6. 종료 방식, 턴 수, 오류·반려와 같은 실행 효율

질문하지 않은 내용을 SOAP에 적어도 정보수집을 한 것으로 인정되지 않는다. 기록에 교육 계획을 적는 것과 환자에게 실제로 교육하는 것도 다르다.

### 5.2 점수 해석

- 공개 샘플 서버가 보여 주는 점수는 참고 점수다.
- 공개 샘플 참고 점수와 공식 평가 점수는 환자 모델·평가 모델·증례가 달라질 수 있어 일치하지 않는다.
- 직접 세션 API 결과에 `not_scored` 또는 `total: null`이 있어도, 이를 0점으로 해석하지 않는다. 실행 성공 여부와 점수 제공 여부를 분리한다.
- 이 저장소가 transcript를 CPX API로 다시 채점해 표시하는 경우, 반드시 `팀 CPX 참고점수`로 표시한다.
- `팀 CPX 참고점수`를 `NOVA 공식 점수`로 바꾸거나 평균에 섞지 않는다.

## 6. SOAP 제출 계약

진료 종료 시 `DIAGNOSE`는 다음 구조를 보낸다.

```python
from nova_sdk import empty_record

note = empty_record()
note["S"]["cc"] = "C.C : 인후통\nOnset : 내원 1일 전"
note["S"]["ros"] = "Fever/Chill (+/-)\nCough (+)\nDyspnea (-)"
note["O"]["exam"] = "V/S : BT 37.3℃ (턴 3)"
note["A"]["evidence"] = "#1. 급성 인두염\n- 근거 : 1일 전 시작된 인후통, 인두 발적"
note["P"]["disposition"] = "외래 경과 관찰"

client.diagnose(note=note, diagnosis="급성 인두염")
```

HTTP 개념 구조:

```json
{
  "action": "DIAGNOSE",
  "request_id": "고유 요청 ID",
  "note": {
    "S": {"cc": "", "hpi": "", "pmh": "", "fh": "", "sh": "", "ros": ""},
    "O": {"exam": "", "tests": ""},
    "A": {"evidence": "", "differential": ""},
    "P": {"tests": "", "treatment": "", "disposition": "", "follow_up": "", "education": ""}
  },
  "diagnosis": "주진단 하나"
}
```

### 6.1 고정 필드 전체 목록

| 영역 | 키 | 한국어 의미 | 작성 내용 |
|---|---|---|---|
| S | `cc` | 주호소 | 주호소, 시작 시점, 통증이면 NRS·부위·양상·기간 |
| S | `hpi` | 현병력 | 시작, 경과, 양상, 악화·완화 요인, 동반 증상, 이전 진료, 내원 경위 |
| S | `pmh` | 과거력·약물·알레르기 | 과거 질환, 수술력, 복용약, 알레르기와 확인한 음성 |
| S | `fh` | 가족력 | 관련 가족력과 확인한 음성 |
| S | `sh` | 사회력 | 흡연, 음주, 직업, 노출 등 |
| S | `ros` | 계통 문진 | 관련 계통의 양성·음성 목록 |
| O | `exam` | 진찰 소견 | 활력징후와 실제 시행한 신체진찰 결과, 결과를 받은 턴 |
| O | `tests` | 검사 결과 | 실제 수령한 검사 결과와 턴. 예선은 비워 둠 |
| A | `evidence` | 진단 근거 | 주진단별 수집 사실과 그 해석 |
| A | `differential` | 감별진단 | `r/o 진단명 : 이유` 형식의 감별 목록 |
| P | `tests` | 추가 검사 계획 | 필요한 검사와 이유. 이미 시행한 결과처럼 쓰지 않음 |
| P | `treatment` | 치료 계획 | 약물·처치·금기·생활 안내 등 |
| P | `disposition` | 처치 결정 | 귀가, 외래 추적, 입원, 의뢰, 응급 처치 등 |
| P | `follow_up` | 추적·안전망 | 재진 시점, 결과 확인, 즉시 재내원할 경고 증상 |
| P | `education` | 환자 교육 | 환자에게 설명할 내용. 실제 설명은 SAY로 별도 수행 |

필드는 정해져 있다. 필드를 누락하거나 임의 필드를 추가하면 `INVALID_RECORD_FIELDS`가 될 수 있다. `A`에는 `diagnosis` 키를 만들지 않는다. 주진단은 `diagnosis` 인자로 별도 제출한다.

### 6.2 빈칸·미확인·음성·미시행·계획

| 상태 | 의미 | 기록 예 |
|---|---|---|
| 빈칸 | 해당 칸에 기록할 내용이 없음 | `""` |
| 확인된 없음·음성 | 실제로 질문·확인했고 없었음 | `Allergy (-)` |
| 미확인 | 아직 묻거나 얻지 못함 | `Allergy ( )` |
| 미시행 | 해당 진찰·검사를 하지 않음 | `복부 진찰 미시행` |
| 계획 | 앞으로 할 일 | `필요 시 CBC 확인 계획` |

`미확인`을 `없음`으로 바꾸지 않는다. `계획`을 `시행 결과`처럼 쓰지 않는다. 공개되거나 수령한 수치·단위·참고범위는 그대로 옮기고 추정하지 않는다.

## 7. S 작성 세부 가이드

### 7.1 `S.cc` 주호소

주호소는 환자가 실제로 말한 표현과 확인한 핵심 정보를 짧게 정리한다.

```text
C.C : 인후통
Onset : 내원 1일 전
통증평가 : NRS 4점, 목, 따끔거림
```

주호소를 의사가 임의로 더 전문적인 병명으로 바꾸지 않는다. 병명은 A와 별도 주진단에 둔다.

### 7.2 `S.hpi` 현병력

다음 순서를 기본으로 한다.

1. 언제 시작했는가
2. 어떻게 변했는가
3. 양상·정도·빈도는 어떠한가
4. 악화·완화 요인은 무엇인가
5. 함께 있는 증상과 없는 증상은 무엇인가
6. 이전 진료·복용약·내원 경위는 무엇인가

예:

```text
내원 1일 전 시작된 인후통으로 내원함. 기침이 동반됨.
통증 정도와 악화·완화 요인은 미확인. 호흡곤란은 부인함.
```

### 7.3 `S.pmh`, `S.fh`, `S.sh`

항목형 병력은 확인한 음성도 기록한다.

```text
DM / HTN (-/-)
Previous stroke (-)
Tbc / hepatitis (-/-)
Op. Hx (-)
Medicine history ( )
Allergy ( )
```

괄호를 비워 둔 것은 미확인이다. 모든 항목에 자동으로 `(-)`를 채우면 질문하지 않은 내용을 사실처럼 기록하게 된다.

### 7.4 `S.ros` 계통 문진

관련 위험 신호를 직접 확인하고, 양성뿐 아니라 확인한 음성도 쓴다.

```text
Fever/Chill (+/-)
Cough (+)
Dyspnea (-)
Chest pain (-)
```

증례와 무관한 ROS를 길게 나열하는 것은 정보수집과 효율 모두에 불리할 수 있다.

## 8. O 작성 세부 가이드

### 8.1 `O.exam`

- 시작 정보로 제공된 활력징후와 직접 확인한 진찰 결과를 분리한다.
- 진찰 결과를 받은 턴 번호를 가능하면 붙인다.
- 시행하지 않은 진찰을 정상으로 기록하지 않는다.
- 여러 부위의 결과를 한 번에 받았다고 쓰지 말고 실제 EXAM 응답에 맞춰 기록한다.

```text
V/S : BT 37.3℃ (턴 3)
H/E/E/N/T : 인두 발적 (+) (턴 4)
Chest : Clear (턴 5)
```

### 8.2 `O.tests`

검사 결과를 실제로 받은 경우에만 기록한다. 예선에서 TEST가 제공되지 않으면 비워 둔다. 필요한 검사는 P의 `tests`에 계획으로 쓴다.

```text
Hb 9.8 g/dL (L), MCV 72 fL (L), ferritin 8 ng/mL (L) (턴 9)
```

수치·단위·참고범위를 환자가 말하지 않았거나 환경에서 제공하지 않았다면 추정하지 않는다.

## 9. A 작성 세부 가이드

### 9.1 별도 `diagnosis`

- 주진단은 하나만 제출한다.
- SOAP의 `A` 안에 `diagnosis` 필드를 만들지 않는다.
- 주진단 문자열은 기록의 `evidence`와 일관되어야 한다.
- 환자가 말한 진단을 그대로 주진단으로 확정하지 말고 수집된 사실과 감별을 검토한다.

### 9.2 `A.evidence`

근거는 내부 사고 과정 전문이 아니라 수집한 사실과 판단을 연결하는 간결한 설명이다.

```text
#1. 급성 인두염
- 근거 : 1일 전 시작된 인후통과 인두 발적, 발열·호흡곤란은 확인되지 않음
```

없는 수치·진찰·병력을 근거에 추가하지 않는다.

### 9.3 `A.differential`

가능성이 있거나 놓치면 위험한 감별을 이유와 함께 적는다.

```text
r/o 세균성 인두염 : 편도 삼출물과 경부 림프절 소견 미확인
r/o 심부 경부 감염 : 연하곤란·호흡곤란과 목 부종 확인 필요
```

질환명만 나열하지 말고, 현재 사실과 무엇이 맞거나 부족한지 쓴다.

## 10. P 작성 세부 가이드

### 10.1 `P.tests`

검사명과 이유를 적는다. 예선에서는 실제 TEST 결과를 적는 칸이 아니다.

```text
경고 증상 또는 활력징후 이상 시 CBC 및 관련 검사를 고려하고 결과에 따라 재평가
```

### 10.2 `P.treatment`

현재 수집한 사실과 금기를 고려한 치료 계획을 쓴다. 이미 시행하지 않은 처치를 시행한 것처럼 쓰지 않는다.

### 10.3 `P.disposition`

환자의 현재 위험도와 상태에 맞춰 귀가·외래 추적·입원·의뢰·응급 처치를 결정한다.

### 10.4 `P.follow_up`

재진 시점과 결과 확인 방법을 적고, 즉시 다시 와야 하는 경고 증상을 구체화한다.

### 10.5 `P.education`

SOAP에는 교육 계획을 적을 수 있지만, 의사소통 점수에 반영되려면 실제 진료 중 `SAY`로 설명해야 한다. 마지막에 다음을 환자 말투로 설명하고 이해·질문을 확인한다.

- 현재 판단과 불확실성
- 지금 할 일
- 복용·생활 주의점
- 악화 시 즉시 와야 하는 증상
- 언제 어디로 재진할지

## 11. 진료 종료 전 체크리스트

- [ ] 주호소에 맞는 위험 신호를 직접 물었다.
- [ ] 필요한 과거력·약물·알레르기를 확인했다.

- [ ] 한 턴에 여러 질문·여러 진찰을 묶지 않았다.

### 기록

- [ ] `S/O/A/P`의 모든 고정 키가 존재한다.

- [ ] `SAY`·`EXAM` 입력이 NFC 30 코드 포인트 이내다.
- [ ] 공개 샘플 대본을 실행 입력에 몰래 주입하지 않았다.

## 12. 공개 샘플·로컬 CPX·공식 점수 표시 규칙

우리 화면과 결과 JSON에서는 점수 출처를 반드시 구분한다.

| 표시명 | 의미 | 공식 점수인가 |
|---|---|---|
| `NOVA 공개 샘플 참고점수` | NOVA 샘플 검증 화면이나 서버가 제공한 샘플 결과 | 아니오. 공개 샘플 참고값 |
| `팀 CPX 참고점수` | 같은 transcript·SOAP를 우리 CPX judge로 재채점한 결과 | 아니오 |
| `NOVA 공식 평가점수` | 공식 평가 실행에서 공식 서버가 반환한 결과 | 예 |
| `미채점` | 실행은 되었지만 점수 객체가 없거나 `not_scored`인 상태 | 0점 아님 |

특히 다음을 금지한다.

- `null`을 숫자 0으로 표시
- 팀 CPX 점수를 NOVA 샘플 점수로 표시
- 샘플 점수와 공식 점수를 하나의 평균에 섞기
- 로컬 개발 키트의 결과를 서버 평가 결과로 표시
- 공개 샘플 모범 기록을 공식 만점 답안으로 표시

## 14. 공식 규칙과 우리 로컬 규칙의 차이

우리 CPX 엔진은 팀의 연습·비교를 위해 추가 기능을 제공한다.

- 환자 7명과 NOVA 공개 샘플 3건을 한 화면에서 관리
- 대화 목록·SOAP 필드·턴별 평가를 웹에서 복기
- 팀 실험 라벨·제목·메모 저장
- 기존 CPX 채점과 NOVA 공개 샘플 케이스를 같은 화면에서 비교
- 공개 샘플 transcript를 팀 CPX judge로 별도 재채점

이 기능들은 대회 서버의 일부가 아니다. 대회와 비교할 때는 행동 규칙·SOAP 구조·50턴·30자 제한을 기준으로 삼고, 점수와 내부 프롬프트는 별도로 취급한다.

## 15. 제출 계약 요약

제출 ZIP은 공식 시작 패키지의 계약을 따른다.

```text
submission.zip
├── run.py
├── requirements.txt
└── nova_sdk.py
```

주의할 점:

- 서버가 제공하는 SDK와 `empty_record()` 구조를 기준으로 한다.
- 실행 중 인터넷에서 모델·데이터를 내려받는 방식은 사용하지 않는다.
- 추가 패키지는 공식 허용 방식과 고정 버전을 따른다.
- 예선 증례마다 지정 Doctor API를 최소 1회 호출해야 한다.
- `run.py`의 준비·상담 흐름은 공개 샘플과 공식 평가에서 재사용 가능하도록 상태를 증례별로 초기화한다.
- 공식 제출 ZIP에는 공개 샘플 대본을 정답 데이터로 몰래 넣어서는 안 된다.
